## 5. 설계 확인과 예상 PR 질문

핵심 구현은 기존 `SimulatedAmr.Advance(double elapsedSeconds)`를 유지한다. 시간 검사 후 경유점을 순서대로 진행하고, 도달에 사용한 시간을 빼서 다음 구간에 사용한다. 최종 목표 좌표를 그대로 대입해 정지하며 설정 속도와 현재 속도를 분리한다. #33 계산에는 새 Task·큐·Lock·소켓·이벤트 구독이 없다. 같은 객체의 읽기·갱신은 호출자가 순차 수행해야 하며 현재 Runner도 한 곳에서 Advance를 호출한다. 프로세스 내부의 계산 순서가 MQTT 전달 순서·중복·유실까지 보장하지는 않는다.

단순한 sqrt(dx*dx+dy*dy)·speed*time과의 비교: 현재 2의 지수로 크기를 나누는 방식은 유한 입력의 중간 overflow/underflow를 줄이며 새 패키지 없이 기존 수치 경계 시험을 유지한다. 단순식은 읽기 쉽지만 현재 허용하는 큰/작은 유한값의 곱·차·거리에서 표현 범위를 넘을 수 있다. 현재 방식은 보조 계산을 읽어야 하는 유지보수 비용이 있다. 별도 성능·메모리 벤치마크는 하지 않았다. 경유점 진행에 필요한 소수의 상태만 보관하며, 한 번의 호출은 통과한 경유점 수에 비례하는 계산을 수행한다. 운영 좌표 범위가 확정되거나 대규모 경로의 성능 요구가 생기면 계산 단순화·최적화를 다시 판단한다.

1. **왜 실제 타이머를 계산에 넣지 않나?** 경과 시간 직접 주입으로 같은 입력의 위치·상태·도착을 안정적으로 확인하기 위해서다. 시계·대기·취소·실제 종료 책임은 기존 #34 Runner에 있다. 취소 요청만으로 실제 루프 종료를 보장하지 않는다.
2. **0초·잘못된 시간이 경로 진행을 바꿀 수 있나?** 0초는 조기 반환하고 잘못된 시간은 변경 전에 예외로 거부한다. 초기·이동·도착 후 상태까지 시험했다. 동일 위치 선행점은 생성 때 건너뛰며 원래 설정은 보존한다.
3. **이 PR을 #33만의 결과로 병합해도 되나?** 기존 PR #36 head에는 후속 기능도 포함되어 있고 기존 본문에는 최초 #33 범위가 남아 있다. 이번에는 계산 범위의 명세 대조와 전용 회귀만 수행했다. PR 범위·본문의 정합성, 나머지 코드 리뷰·승인·병합은 사용자가 요청할 후속 단계다.
