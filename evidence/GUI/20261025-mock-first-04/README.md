## 선택한 구조와 한계

Core에는 인터페이스·읽기 전용 record/ImmutableArray만 두고 GUI는 Core만 참조한다. 통신 DTO를 옮기지 않고 폴더를 미리 세분하지 않았다. 두 Mock 클래스는 상태를 공유해 요청 접수 직후 같은 ID로 조회할 수 있다. 초기 스냅샷 생성과 등록, 상태 변경과 요청 등록은 같은 잠금에서 처리한다. 이것은 프로세스 내부 보장이며 MQTT 전달 순서·무손실 보장이 아니다.

구독별 64항목과 앱 실행당 요청 128건은 Program에 명시한 **Mock 개발 설정**이다. 초과 시 `AmrResyncRequiredException`으로 해당 구독을 종료하고 화면이 새 초기 스냅샷을 받는다. 모든 사건 보존은 이 스트림의 책임이 아니다. Mock에는 주기/발행 작업이 없어 공급자 종료는 큐 정리·독자 해제로 끝난다. 실제 운영 버퍼·전송/종료 Timeout은 미정이다.

현실적인 대안은 변경분만 보내기와 처음부터 화면별 UserControl로 나누기다. 전체 스냅샷은 두 장비·제한된 명령 자료에서 복구와 검증이 단순하지만 장비/요청 수가 커지면 복사·전송 비용이 증가한다. 화면 분리는 재사용에 유리하지만 이번 작은 확인 폼에서는 파일과 연결 코드가 늘어난다. 실제 규모·갱신 빈도 측정 또는 영역별 독립 변경이 필요할 때 각각 전환한다. 대안의 성능 비교 시험은 수행하지 않았다.

예상 검토 질문:

1. **Core 프로젝트를 지금 만드는 이유는?** 실제 공급자와 Mock이 공유할 조회/명령 계약을 GUI 구현과 분리하기 위해서다. Core의 실제 업무 처리는 아직 없다.
2. **Mock 성공이 실제 AMR 완료를 의미하는가?** 아니다. 시험 버튼이 지정한 결과이며 Publish=MockOnly, ACK 원본/시각은 null이다. 위치·State를 완료로 조작하지 않는다.
3. **취소·닫기가 이미 접수한 명령을 취소하는가?** 아니다. 접수 잠금 안의 취소 확인 이전에는 기록하지 않고, 이후에는 ID를 반환·보존한다. 폼은 자기 작업·구독만 정리하고 앱 시작 지점이 공급자를 종료한다.
